/goal

Implement the next Phase 12 vertical slice: Stage 2 versioned native transaction API and compatibility migration across Node/OpenGL and Wasm/WebGPU.

Primary outcome:
Both runtimes accept the same schema-version-1 structural transaction through a shared native ApplyCommit implementation. The complete transaction is parsed and validated before any operation mutates live state. Each successfully applied transaction produces one authoritative sequence, one native revision increment, and an explicit destruction result. Existing structural exports delegate to this path as single-operation transactions, preserving public JavaScript behavior and all Stage 1 lifetime guarantees.

This slice delivers a usable multi-operation native API and migrates the ordinary runtime path onto it. It does not batch Fabric work at completeRoot or establish atomic visibility, speculative-work isolation, or reparent-safe final reachability. Those are Stage 3; rendering and invalidation scheduling remain Stage 4. A transaction revision in this slice must not be described as a Fabric commit revision or a presented-frame guarantee.

Starting evidence:
- Commit 62f46a4 delivered Stage 1 cleanup. Both real runtimes passed 1,000 cycles with zero growth across all ten lifetime counters, retaining only one fixed empty hierarchy entry for virtual container 0.
- Native suites passed 333 tests each on Windows and Linux. The Fabric suite passed 14 scenarios in each isolated development/production process, including the remaining narrow expected failures.
- Node and Wasm setChildren return the same JSON array of actual destroyed IDs. ReactivePlusPlus subject delivery is synchronous; results are completed after native tree locks are released. Preserve this completion boundary for existing callers.
- XF-LIFE-001/002/003/006/007/010 are passing invariants. XF-LIFE-004/005/008/009 still characterize pre-completeRoot publication, same-native-ID reparent destruction, incomplete cross-parent clone staging, and abandoned Suspense work.
- The cleanup record reports material Wasm latency and Node idle-CPU regressions, plus missed 120 Hz rate targets. These are open measurements, not established causes or universal CI thresholds.
- Hosted results in the cleanup record describe the checks known at that time. Inspect current hosted status separately; do not infer that committed configuration or successful local runs establish hosted coverage.

Deliverables:

1. Define and implement the shared version-1 contract.
   - Add owned native transaction/result types and matching TypeScript binding types. Keep Node and Wasm schema parsing, operation validation, result semantics, and error codes in one common implementation wherever possible.
   - Support ordered create, patch, setChildren, and appendChild operations, including multiple operations in one transaction and references to nodes created earlier in that transaction. JSON is appropriate for this first version.
   - Define required fields, schemaVersion, surface identity, sequence/correlation fields, numeric ranges, root handling, and unknown-field policy. Public string IDs remain JavaScript bindings and cannot overwrite native numeric identity.
   - Define how surface IDs relate to the current Fabric root and virtual container 0. A single supported surface is sufficient for this slice if unsupported surfaces are rejected explicitly. Do not silently alias different surfaces to the same tree or introduce full multi-window support.
   - Make one authority allocate structural application order across both the new API and compatibility exports. Prefer native allocation per XFrames instance; distinguish any caller correlation sequence from the authoritative native sequence. Define duplicate, stale, gap, and overflow behavior for caller-supplied ordering fields if supported.
   - Return a shared result containing accepted sequence, surface, native revision, and actual destroyed IDs. Define rejected-input results/errors so callers can distinguish rejection from successful application without log parsing. Finalize the exact wire spelling in the implementation record with valid and invalid examples.
   - Keep sequence/revision state available with diagnostics disabled. Define initialization, empty-batch, accepted no-op, rejected-batch, and teardown behavior. Diagnostics resets must not reset ordering or revision state for a live runtime. Avoid lossy JavaScript integer conversion.

2. Parse and validate the entire batch before mutation.
   - Parse once into an owned representation and validate all operations before executing the first operation. A valid prefix followed by an invalid final operation must leave native elements, hierarchy, Yoga, widget data, subjects, destruction output, and revision unchanged.
   - Cover malformed JSON, unsupported versions/operations/surfaces, missing or incorrectly typed fields, unsafe/out-of-range IDs, invalid element types, attempts to overwrite numeric identity, and invalid structural relationships supported by the validation contract.
   - Validate references and relationships against the ordered operations and current native state. A validation-only working model is acceptable; it must not create live Elements, Yoga nodes, subjects, or widget resources. Validate synchronously consumed props sufficiently to avoid predictable type/shape errors halfway through application.
   - Define policies for duplicate creates/children, missing targets, self-links/cycles, forward references, and references to nodes destroyed earlier in the batch. Preserve established compatibility no-op behavior for stale legacy calls, and document any deliberate difference from the new explicit API rather than changing it accidentally.
   - Keep validation and subsequent application serialized against competing structural mutations, so checks cannot become stale before use. Respect the existing lock order and avoid recursively taking tree locks inside existing mutation helpers.
   - Surface unrelated application/runtime exceptions honestly. Full rollback after arbitrary allocation, resource, or widget-constructor failure is outside this slice; document that limit and never report a partial apply as a successful transaction.

3. Introduce the common native application path and migrate compatibility exports.
   - Expose equivalent applyCommit entry points through Node-API and Emscripten, backed by the shared C++ ApplyCommit implementation. Exercise genuine multi-operation batches through both exported bindings.
   - Route setElement, patchElement, setChildren, appendChild, and their externally used Queue* entry points through the same validated structural application path as one-operation transactions. Keep private mutation helpers distinct from public dispatch to avoid recursive re-enqueueing or duplicate application.
   - Preserve current valid-call argument conventions, return shapes, synchronous completion, public widget APIs, and ordinary Node/Wasm wrapper behavior. In particular, legacy setChildren still returns its destroyed-ID JSON array; no mandatory initialization argument is added.
   - Apply operations in their declared order using Stage 1 destruction semantics. Collect actual destroyed descendants once, preserve survivor identity/state and resource destructors, and return results only after native tree locks are released. Define or reject same-batch destruction/recreation of the same numeric ID so an acknowledgment cannot invalidate a newly live owner.
   - Increment the native revision exactly once after successful application of a transaction, regardless of operation count. Compatibility transactions and direct batches must share ordering and revision state; rejected transactions must not increment the revision.
   - Preserve cleanup of Fibers, native target records, forward/reverse public mappings, registration leases, internal subjects, and stale event/handle rejection. The new result contract must be consumable by the existing cleanup mechanism without relying on diagnostic snapshots or wholesale registry resets.
   - Give transaction payloads, results, subject records, and subscriptions explicit bounded ownership and teardown. Preserve ReactivePlusPlus/RxJS; bounded replay must not unnecessarily retain large completed batch/result payloads.
   - Preserve ordering of existing imperative widget calls relative to synchronous structural calls. Do not migrate all widget commands into the new wire schema or claim a total ordering domain for asynchronous resources in this slice.

4. Establish transaction regression gates on the actual shared path.
   - Extend native tests through real queue/subject delivery, not only pure parser helpers. Verify exact results, revisions, surviving widget content, hierarchy/Yoga consistency, destruction, and recovery after rejected transactions.
   - Test several-operation create/attach/patch/reorder/remove batches; virtual-root partial removal and populated unmount; malformed final operations; duplicate/missing IDs; unsupported surfaces; empty/no-op policy; and mixed legacy/new API ordering. Verify that invalid batches cause no mutation or destruction and the next valid batch still works.
   - Exercise the same valid and invalid wire fixtures through the current-source Node and Wasm bindings. Compare semantic results, error classifications, revisions, and actual native state; a fake module alone is not binding parity evidence.
   - Extend the isolated development/production Fabric fake-binding harness to model the compatibility transaction path and destruction results. Keep ordinary wrappers on the tested migration path and preserve Strict Mode, ID rebinding, delayed effects/events, stale handles, and teardown checks.
   - Prove that one multi-operation API call gives one native revision increment and that compatibility calls advance that same state once each. Capture enough bounded diagnostics to identify a failed sequence/operation without adding a durable recorder or full frame-correlation system.
   - Keep all six resolved cleanup/identity defect IDs as ordinary passing invariants. Keep XF-LIFE-004/005/008/009 executing with narrow signatures for Stage 3. Review unexpected passes and explain secondary signature changes; do not silently skip, widen, or relabel the underlying defects as fixed.

Keep raw reports and generated artifacts out of source changes.

Scope and constraints:
- Preserve Fabric, React 19.2.3, RN 0.87.0, RxJS, ReactivePlusPlus, Yoga, Dear ImGui, and public component APIs. Modify owned host/binding seams rather than generated renderer snapshots.
- Keep Stage 2 separate from Stage 3: no prospective Fabric collector, completeRoot batching, final committed-reachability destruction, reparenting repair, or abandoned-work sweep. Full preflight validation is required; atomic visibility of a successfully applying multi-operation batch is not this slice's acceptance claim.
- Keep individual-operation mutation behavior and render policy intact except where needed for the common transaction contract. Do not implement invalidation scheduling, frame-revision correlation, trace/replay, automation APIs, operation coalescing, or binary transport.
- Do not add a general asynchronous shutdown redesign, new widgets, macOS support, multi-window rendering, publishing, dependency upgrades, or CMake consolidation. Use the authoritative npm workspace lockfile and documented toolchains.
- Map/Canvas benchmarks, hardware WebGPU baselines, ubx-monitor integration, and Electron/GPUIX comparisons remain open. Stage 2 completion does not complete Stage 0 coverage or the Stages 0-4 milestone.
